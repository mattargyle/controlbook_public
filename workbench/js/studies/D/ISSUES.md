# Design Study D: issues found in the book and repo

As of 2026-10-04. This covers Design Study D (the mass-spring-damper): problems D.2–D.18 and D.P.6, controlbook.pdf pp. 377–383.

D has no worked solutions in the book, so there are no "wrong printed answers" to report. Most items are **ambiguous problem statements** that change a numerical answer, plus a few repo inconsistencies. Every number below was derived from m = 5 kg, k = 3 N/m, b = 0.5 N·s/m and F_max = 6 N. `tools/regress_D.py` cross-checks it against python-control.

Page numbers are PDF pages (book page + 8).

## Ambiguous or underspecified problem statements

| Problem | PDF page | Issue | Effect / workbench choice |

| D.4(c) feedback linearization | 378 | The plant is already linear, so "feedback linearization" has no unique answer: F_fl = 0, F_fl = kz (cancel the spring, as the book cancels gravity for the arm, Eqs. 4.6–4.7, p. 64) and F_fl = kz + bż (z̈ = F̃/m) all give a linear model. | The D.4(c) check accepts any F_fl whose resulting z̈ is linear in (z, ż, F̃) and consistent with the plant. The solution uses F_fl = kz and mentions the others. |
| D.5(a) "convert to the s-domain" | 378 | The book does not say which form the s-domain equation should take. | The check asks for F(s) as a function of Z(s) (zero initial conditions), which is unique, so the student writes (ms² + bs + k)Z(s) without being shown that form. |
| D.15, D.16, D.17 lettering | 382–383 | D.15 and D.17 have no lettered parts, and D.16 starts with an unlettered plotting task. | The workbench splits them into parts in the book's order: D.15 "draw by hand" (marked done) then "compare with bode"; D.16 "Bode plots" (info) then (a)–(c); D.17 margins, the open/closed-loop Bode plot (info), and bandwidth vs. crossover. |
| D.7–D.8 (PD architecture) | 379 | Fig. 7-2 PD on this type-0 plant gives Z/Z_r = (k_P/m)/(s² + …), so a 1 m step settles at k_P/(k + k_P): 0.6 m with the D.7 gains and 0.504 m with D.8(a). D.10 then speaks of "the steady state error caused by the uncertain parameters," which only makes sense if the controller also supplies the equilibrium force F_e = k z_e with z_e = z_r. | Explore mode offers a "spring compensation" toggle: `F = k z_r + F̃` or none (Fig. 7-2 exactly). It moves no poles. The default is none on D.7–D.P.6 and `F = k z_r + F̃` on D.10. In Work mode the student writes the controller (D.7(d), D.8, D.10(c)), so the choice is theirs: the D.7(d) and D.8(a) checks compare z(t) with the design with and without F_e and accept either. The D.7(b) answer is the Fig. 7-2 transfer function, as asked. |
| D.8(a) "verify the step response" | 379 | Without F_e the response never reaches 90% of the 1 m step, so a rise time against the commanded step does not exist. | The check runs the student's controller on a 1 m step and compares z(t) with the design (within 2% of the step, nominal and a second parameter set, with or without F_e). The 10–90% rise time against the final value is 1.93 s, with 4.6% overshoot, either way (2.2/ω_n is exact only near ζ = 0.707). The page's step-response panel still measures against the commanded step. |
| D.8(b) "just saturates" | 379 | The answer depends on the architecture. Without F_e: F(0⁺) = k_P·1 m ≤ 6 gives k_P = 6, ω_n = 1.342, t_r = 1.640 s (k_D = 8.89). With F_e = k z_r: F(0⁺) = 3 + k_P ≤ 6 gives k_P = 3, ω_n = 1.095, t_r = 2.008 s (k_D = 7.17). The D.8(a) design (k_P = 3.05) then demands 6.05 N, so it saturates very slightly. | The check probes the student's controller with a 10 m error (its output must stay within ±F_max), then runs a 1 m step from rest: the peak demand must reach 95% of F_max with at most 2 samples at the limit, whichever architecture the student chose. The solution shows both cases. |
| D.P.6, D.10, D.11, D.13 "designed in D.8" | 380–381 | These don't say whether to use the D.8(a) gains (t_r = 2 s) or the D.8(b) gains. | The workbench uses the D.8(a) specs (t_r = 2 s, ζ = 0.7), which the problem gives, so no D.8(b) answer leaks into later tabs. The Explore knobs accept any t_r. |
| D.10(c) k_I | 380 | No value or criterion is given. | Workbench choice: the student's PID runs on a plant with a fixed α = 0.2 mismatch draw (Δm = +15%, Δk = −18%, Δb = +10%), and the error just before the first switch (t = 25 s) must be under 2% of the 0.5 m step. With the D.8(a) gains and F_e = k z_r, k_I = 0.5 gives 6.0 mm and k_I = 0.75 gives about 1.5 mm, against a 10 mm limit (without F_e, k_I = 0.75 gives 6.0 mm). Without an integrator: 49 mm. D.P.6's own criterion (pair within 10% in \|p\|, also a workbench choice) allows k_I ≲ 0.8, so any k_I in 0.5–0.8 passes both checks. The reference solution uses k_I = 0.75. |
| D.12, D.13, D.14 poles | 381–382 | The integrator pole, the observer poles and the disturbance-observer pole are left to the student. | D.12(a) fixes p_I = −1 (a workbench choice) so its gains and the student's controller can be compared with a design; D.12(c), D.13(c) and D.14(b) check behaviour, so any poles that pass are fine. The reference solution uses p_I = −1, observer ω_n = 11 rad/s (10× the controller), ζ = 0.707, and p_d = −5. |
| D.12(a) anti-windup | 381 | It is asked for, but there is no method or threshold. | With integral state feedback the reference enters only through the integrator, so a reference step never asks for more force than the final value (1.51 N peak for a 0.5 m step): steps can't provoke windup. The check instead starts the mass at z = 1 m with z_r = 0 and F_max lowered to 1.5 N (F saturates for about 3 s): z may undershoot by at most 0.44 m. No anti-windup gives 0.55 m, holding the integrator while saturated 0.33 m, back-calculation 0.08 m, and the unsaturated design 0.31 m. Integrating only while \|ż\| is small (Listing 10.2) changes the unsaturated tracking of this controller, so it fails the design comparison before the windup test. A target that saturates indefinitely (F_max below k z_r) would lock the "hold while saturated" scheme at the limit, so the check avoids it. |
| D.13(c) estimate check | 381 | — | The repo's observer timing (RK4 over T_s with y at the end of the step) makes ẑ lag for a moment after each reference switch (about 1 mm). The check reads \|z − ẑ\| and \|ż − ż̂\| only in the 3.5 s before each switch (limits 0.1 mm, 1 mm/s; the solution gives about 10⁻⁶). Returning ẑ = z (no observer) passes this part; D.13(e) catches it. |
| D.13(e) | 382 | "Observe … steady state error" | With a 10×-faster observer, the bias is small: z − ẑ = −C(A − LC)⁻¹B·d = b₀d/β₀ = 0.2·0.25/121 = 0.41 mm. Use a slower observer to see it clearly. The check runs the student's saved D.13(c) controller with d = 0.25 N and passes when the mean bias over the 10 s before the first switch is not zero (> 1 µm). |
| D.14(b) | 382 | "Verify that the steady state error in the estimator has been removed." | With the reference observer, the bias without the disturbance observer is under 1 mm, against 1 mm measurement noise. The check runs the student's controller with the mismatch, d = 0.25 N and the noise, averages z − ẑ over the 10 s before the first switch and requires < 0.2 mm (about 0.03 mm with the disturbance observer, 0.83 mm with the D.13 controller), and the mean tracking error over the last 0.5 s before it < 2.5 mm. |
| D.15 | 382 | "Force F̃ to position z̃" | The plant is already linear, so F̃ = F and z̃ = z for every equilibrium. |
| D.16(b) | 383 | The book's rule γ_din = 1/\|C(jω_din)\| (Eq. 16.8–16.9, p. 290–291) assumes \|PC\| ≫ 1 at ω_din. Here \|PC(j0.1)\| ≈ 3.3 (10.4 dB) with the D.10 gains. | 1/\|C(j0.1)\| = 10.2% vs. the exact \|P/(1+PC)\|(j0.1) = 9.1% (k_P = 3.05, k_D = 7.2, k_I = 1, σ = 0.05). The checker accepts either. |
| D.17 bandwidth | 383 | With D.8-style gains (k_D ≫ k_I), the PID zeros are complex (−0.21 ± 0.31j for k_I = 1) and make a notch in \|C\| near √(k_I/k_D) ≈ 0.37 rad/s. \|T\| dips to −4.8 dB around 0.3 rad/s, then recovers. | The "−3 dB bandwidth" is ambiguous: the first crossing is 0.190 rad/s (what `control.bandwidth` returns), while the final roll-off is 2.13 rad/s, just above ω_co = 1.78 rad/s. The checker accepts either; the solution explains the notch. |
| D.17 fixed loop | 383 | The answers depend on the D.10 gains, and D has no book listing of them. | D.17's checks use a fixed loop stated in the parts, not the sliders (so answers don't go stale): the D.8(a) design k_P = 3.05, k_D = 7.2 (t_r = 2 s, ζ = 0.7) plus the D.10 solution's k_I = 0.75 and σ = 0.05. Then PM = 75.2° at ω_co = 1.791 rad/s, GM = ∞, and ω_bw = 0.148 rad/s (first −3 dB crossing, from the PID-zero notch) or 2.142 rad/s (final roll-off), so ω_bw/ω_co = 0.083 or 1.196; either pair is accepted (python-control: PM 75.198°, ω_co 1.7907, bandwidth 0.1474). The sliders still drive the Bode plot. |
| D.17 margins with other gains | 383 | — | The lightly damped resonance can push \|PC\| back above 0 dB. With k_P = 2, k_I = 0.5, k_D = 4 (the tab's placeholder gains), \|PC\| crosses 0 dB three times: PM 133° at 0.18, −171° at 0.43, and 70.7° at 1.28 rad/s. The workbench lists every crossover and reports the one with the smallest \|PM\|, as python-control's `margin` does (checked in `regress_D.py`). |
| D.18 | 383 | Saturation is not mentioned, but F_max = 6 N from D.8 is still in the simulation. The constant-input-disturbance size is not given. | The reference design (PI at 0.5, lead ω = 5 rad/s with M = 30, LPF 50, crossover 5 rad/s, prefilter p = 1) meets every loop-gain spec: PM 59.1°, GM 23.3 dB at 35.6 rad/s, min\|PC\| on ω ≤ 0.1 = 31.8 dB (needs 30.5), max\|PC\| on ω ≥ 500 = −85.5 dB. The workbench uses d = 0.25 N, as in D.12–D.14. |
| D.18 notation | 383 | ω_n means the noise frequency here but the natural frequency everywhere else (including D.11(a)). | Labels say "noise above 500 rad/s." |
| D.18 order | 383 | The bullets list the prefilter before the implementation in state-space form, but implementing a prefilter in code needs the implemented C first. | The parts are: design C(s) (Python coefficient lists), implement C(s) in state space (compared with the workbench running the same C), then add the prefilter in that code (first-step overshoot < 5%). ## Book vs. repo code

| Topic | Book | Repo (`_D_mass/python`) |
| --- | --- | --- |
| Lead filter | Eq. 18.2 (p. 328): C_lead = M(s + ω/√M)/(s + ω√M). DC gain 1, high-frequency gain M. | `loopshape_tools.lead(w, M)` returns tf([√M, w], [1, w√M]) = √M(s + w/√M)/(s + w√M). DC gain 1/√M, high-frequency gain √M: a factor of √M below the book. `_A_arm`'s `get_control_lead` matches the book. |
| `loopshape_tools.py` | — | It is an older version than `_A_arm/python/loopshape_tools.py`: different function names (`lead` vs `get_control_lead`, …) and spec plots drawn as lines instead of points. Code from A will not run against it unchanged. |
| Parameters | m = 5 kg, k = 3 N/m, b = 0.5 N·s/m (p. 377). F_max = 6 N (p. 379). | `massParam.py` leaves them blank (template). The unit comments say "Kg/s^2" and "Kg/s," which equal N/m and N·s/m. `testDynamics.py` encodes m = 5, k = 3, b = 0.5: every vector satisfies z̈ = (F − 0.5ż − 3z)/5. |
| Animation | Fig. 19-1 shows a spring and a damper. | `massAnimation.py` draws the weight and spring only (no damper). The workbench animation draws both. |

## Repo bugs

None found in the D templates beyond the lead-filter scaling above. `testDynamics.py` compares at 1e-14 absolute. With `f = [ż, (F − b ż − k z)/m]`, all ten vectors match the JS model exactly (0.0 error).
