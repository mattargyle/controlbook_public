# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Companion code for the textbook *Introduction to Feedback Control Using Design Studies* (Beard, McLain, et al.; BYU ME EN 431 / EC EN 483). It is teaching material, not a package: there is no build system, packaging, linter config, or test runner. Content is organized by case study and by homework/chapter number from the book.

## Environment and running code

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # requirements.txt is UTF-16; pip handles it
source .venv/bin/activate
```

A `.venv` (Python 3.14, gitignored) already exists at the repo root.

Dependencies: numpy, matplotlib, control (python-control), sympy, dill, pyqtgraph/PyQt6/PyOpenGL. (`.gitmodules` still lists a `python-control` submodule, but the submodule itself was removed in 2021 (commit `aee15aeb`), so `git submodule update` does nothing. Install `control` from pip instead.)

Scripts use flat sibling imports (`import armParam as P`, `from armDynamics import armDynamics`) and load data files by relative path. **Run them from inside their own directory**:

```bash
cd _A_arm/python && python hw13_armSim.py
cd _hummingbird_sim && python h8_hummingbirdSim.py
```

Simulations open matplotlib animation windows and finish with `plt.waitforbuttonpress()`, so they block until a key is pressed.

### "Tests"

There's no test framework. Correctness checks are standalone scripts that compare a student's dynamics against hard-coded expected values and print PASS/FAIL:

- `_D_mass/python/testDynamics.py`, `_E_blockbeam/python/testDynamics.py`, `_F_planar_vtol/python/testDynamics.py`: check `<system>Dynamics.f(x, u)`
- `_hummingbird_sim/test_dynamics.py`: checks `M`, `C`, `dP_dq`, `tau` against `test_matrices.pkl`

Run them the same way: `cd <dir> && python testDynamics.py`.

## Case study layout

- `_A_arm`, `_B_pendulum`, `_C_satellite`: **full worked solutions**. They also include `unsupported_languages/` (legacy MATLAB/Simulink).
- `_D_mass`, `_E_blockbeam`, `_F_planar_vtol`: **student templates only**: param, animation, dataPlotter, signalGenerator, and testDynamics. Students write the dynamics and controllers, so don't expect those files to be here.
- `_hummingbird_sim`: template and simulation for the Hummingbird lab (labs h2–h12).
- `_hummingbird_lab`: hardware lab code. `python_code/hummingbirdLabs.py` talks to an Arduino over serial (`/dev/ttyUSB0`) through a tkinter GUI. `deprecated/labH*` holds older Arduino `.ino`/`.h` firmware.
- `practice_final/`: a separate "rod-mass" system with the same architecture, split into part1–part4 sims.
- `_jupyter/`: Colab notebooks (from AFIT), chapters 7–18. `loopshaping_example`, `observer_example`, `other_examples`, `vtol_path_planner`, `optimal_control_lecture_material`, and `debugging_excercises` are standalone extras.

## Textbook and notes (`book_and_notes/`)

This directory holds the textbook and the user's own notes, and is the primary reference for theory, notation, and homework problem statements. When a question involves the math (equations of motion, linearization, gain formulas, design specs), check here before inferring from the code.

- `INDEX.md`: **start here.** Maps every chapter, section, design-study example (A/B/C), and homework problem (D/E/F) to its PDF page range, and maps code (`hwNN_*`, `ctrl*`) to chapters. PDF page = book page + 8.
- `controlbook.pdf`: the full textbook (488 pages). Read it with the `pages` parameter (at most 20 pages per request), using page numbers from `INDEX.md`. Always take equations, figures, and numbers from the PDF.
- `controlbook.txt`: page-marked `pdftotext` dump, **for search only** (`grep -n` and then find the nearest `===== PDF page N` marker above the hit). Its math is scrambled, so never quote equations from it.
- Personal notes: anything else the user adds to this directory.

`controlbook.pdf` and `controlbook.txt` are matched by `.gitignore`, so the book stays local and is never committed.

## Architecture shared by every case study

Each `<study>/python/` directory follows the same pattern, and the shared pieces are duplicated per directory rather than imported from a common module:

- `<sys>Param.py`: module of physical constants, initial conditions, `t_start/t_end`, `Ts` (dynamics/control rate), `t_plot` (animation rate), and saturation limits. Imported as `P`.
- `<sys>Dynamics.py`: class with `state` (column vector, `np.array` of shape `(n,1)`), `f(state, u)` (xdot), `h()` (output), `rk4_step(u)`, and `update(u)` (saturate → RK4 → return `y`). The constructor's `alpha` randomly perturbs physical parameters by ±alpha to test controller robustness.
- `<sys>DynamicsSympy.py`: alternative dynamics that load a dill-pickled symbolic EOM (`eom_case_study_A/B`) generated by `hw03_*_solving_for_state_variable_form.py`. The hummingbird uses `h2_generate_KE.py` → `h3_generate_E_L.py` with `EL_helper_functions.py` (rotation matrices, extracting M/C coefficients).
- `ctrl*.py`: one controller class per chapter technique: `ctrlPD` (ch 8), `ctrlPID` (ch 9–10), `ctrlStateFeedback` (ch 11), `ctrlStateFeedbackIntegrator` (ch 12), `ctrlObserver` (ch 13), `ctrlDisturbanceObserver` (ch 14), `ctrlLoopshape` (ch 18), and `ctrlLQR`. Gains are computed in `__init__` from tuning parameters (rise time, ζ, pole locations) using `control.place`/`ctrb`/`obsv`. `update(r, y)` returns `u`, or `(u, xhat)` for observer-based controllers.
- `hwNN_<sys>Sim.py`: main loop. The outer loop runs at `t_plot` and updates `<sys>Animation`, `dataPlotter`, and `dataPlotterObserver`. The inner loop runs at `Ts`: `signalGenerator` produces r/d, then `controller.update(r, y)`, then `dynamics.update(u + d)`.
- `hw15/16/17.py`, `loopShaping*.py`, `loopshape_tools.py`: Bode-based frequency-response and loop-shaping design (ch 15–18).

Conventions to preserve:
- `dataPlotter.update(t, states, ctrl, reference=0.)`: the reference argument goes **last** (this changed in Winter 2024; older answer keys pass it in the middle).
- Case study E is the only one that uses an equilibrium state x_e, an equilibrium force F_e, *and* feedback linearization together.
- Case study F force/torque unmixing should be `np.array([[1.0, 1.0], [d, -d]])`. Some branches have the sign flipped.

## Interactive workbench (`workbench/`)

Static HTML/JS pages (no build; open `workbench/index.html`) for working all six design studies with sliders, s-plane pole dragging, and live book equations. Classic `<script>` files on a global `WB` namespace (not ES modules) so it runs from `file://`. Study A lives in `js/systems/arm.js` + `js/chapters/`; studies B–F each live in `js/studies/<X>/` (loaded by its `manifest.js`). Contract for a study: `workbench/STUDY_GUIDE.md`. Keep JS dynamics and controllers identical to the Python `*Dynamics.py` / `ctrl*.py` (sat → RK4 at Ts); `workbench/tools/regress_<X>.py` checks this. `workbench/tools/smoke_test.py` opens every tab in both modes and reports JS errors. Work mode must not give away the form of an answer: derivation parts are Python answers (Pyodide in a sandboxed worker, `js/core/py.js`) and live-math cards that answer a part carry `answers: 'A.3/d'` so they stay locked until it is solved (all six studies). Parts that ask the student to implement a controller, observer, anti-windup, or C(s) (Ch 7–18) are Python `class Controller` answers run in closed loop against the plant (`js/core/myctrl.js`, `WB.py.closedLoop`); in Work mode the plots show the student's controller, never the workbench's (done for study A; B–F still use gain boxes). `workbench/tools/py_test.py` tests the Python parts end to end (needs network). Book/repo errors found: `workbench/BOOK_ISSUES.md`.
